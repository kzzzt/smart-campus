## 一、P0 —— 演示与"核心卖点"相关（评委一跑代码就会暴露）

### 1. 用电高峰预测结构性永远为 0（两个旗舰功能之一是空输出）
- `src/energy/forecast.py:66` 预测曲线 `base = 3000 * 时段系数 * 周几系数`，**理论上限 3000W**；
- 但所有调用都传阈值 **5000W**：`run_demo.py:86`、`webapp/app.py:119` → `peak_count` 永远 = 0，`suggestion` 永远走"用电平稳、无高峰"分支。
- 实测：demo 打印 `检测到 0 个高峰`。
- **更重要**：`forecast.py:60` 只用了 `history[-1]["ts"]` 取起始时间，**历史功率值完全没被用到**——所谓"预测"是硬编码曲线，不是基于数据的预测。这与"基于历史时序预测用电高峰"的宣称不符。

### 2. 能耗告警在 demo 的固定种子下恰好命中 0 个房间
- `src/energy/simulator.py:33` `random.random() < 0.3`（30% 房间违规）；`run_demo.py:69` 用 `seed=2024`。
- 实测：seed=2024 → **0 个告警**；其他种子 42/99/7/1/123 → 1~4 个。
- 结果：demo 里"违规电器检测"和"高峰预测"两个展示点**都是空输出**，演示效果很差，且结果依赖运气、不可复现。

### 3. `rule_detect` 的"持续/连续"语义错误
- `detector.py:34-36` 实际是**累计**超阈值小时数，不是**连续**；注释写"持续超过 N 小时"。
- 实测：0 点、12 点两个**相隔 12h 的孤立尖峰**被判为违规并告警。

### 4. "IoT + 智算视觉双重判定"——视觉通道 0 次执行
- `detector.py:48` `vision_detect()` 硬编码返回 `{"detected": False}`，是占位桩。
- 全仓库 `use_vision=True` 出现 **0 次**（`run_demo.py:80`、`app.py:115`、`test_detector.py:27` 全部 False）。
- 后果：`detector.py:67` 置信度永远是 `medium`，"高置信双重判定"逻辑永远不会触发。README/作品说明书却宣称"IoT+视觉双重判定降低误报"。

### 5. 大模型能力完全未接线（说明书多处宣称与代码不符）
- `src/ai_service/llm.py` 的 `chat()` **全仓库 0 次调用**（仅出现在注释/docstring）。
- `intent.py:74-84` 的"LLM 兜底"是**硬编码 if/elif**，且把 `llm_used` 置 True 但从未真正调用 `chat()`。
- `constraints.py:36` 的 `Constraint` 类**从未实例化** → "遗传算法 + 大模型约束条件理解"里"大模型理解约束" **0% 实现**。
- `constraints.py:21` `preferred_time` 从未被任何代码读取；`constraints.py:22` `conflicts_with` 只在 `genetic.py:70` 读取、但 demo/app/测试**从不赋值** → 是死约束。
- 作品说明书第二节把这些写成"已完成/深度运用"，一旦评委跑真实 Large Model 路径会发现是空壳。

## 二、P1 —— 功能正确性缺陷

### 6. 意图识别比较类型错误（bug 但恰好语义有时对）
- `intent.py:40-44` `if hit and hit > best_score` —— `hit` 是**整数关键词命中数**，`best_score` 是**归一化浮点**。
- 因 `hit>=1` 恒大于任何 `<=1` 的分数，**实际选择 = "dict 顺序里最后一个命中的意图"**，与匹配强度无关。
- 实测："我想请假，这会影响到奖学金吗" → `scholarship`；"请假会不会影响学籍" → `status_change`。
- 置信度被关键词表长度稀释：`status_change` 7 个词 → 0.143，低于 `intent.py:74` 的 0.25 阈值，**每次都会触发假的"LLM 兜底"分支**。
- 另：`leave` 与 `status_change` 关键词表都含"休学"（`intent.py:18,20`），同义词重叠。
- 修法：先用 `score = hit/len(kws)` 再参与比较，或直接用显式优先级/评分。

### 7. 遗传算法忽略每周学时 & 缺"同班冲突"维度
- `constraints.py:19` 定义 `hours_per_week`（每周几个时段），但 `genetic.py:88-94` 的染色体**每门课只有 1 个基因**。
- 实测：6 门课（学时 2~4）→ 只出 6 行，每课 1 个时段；20 个时段大量空置 → "解决复杂排课冲突"能力上限很低。
- `Course` 没有班级/专业字段 → **同一班级的两门课可以被排进同一时段**（真实排课最重要约束之一缺失）。
- 缺：连堂、教师时间偏好、实验室容量/设备软约束。

### 8. 遗传算法边界崩溃
- `genetic.py:97` `random.randint(1, len(a)-1)` → **单门课程时 `ValueError: empty range`**（实测崩溃）。
- `genetic.py:117` `pop_size // 5` → **`pop_size < 5` 时 elites 为空 → `random.choice([])` IndexError**（实测崩溃）。
- 无早停、无"冲突数"报告、适应度未归一化。

### 9. 教室分配：占位记账与实际输出不一致
- `classroom.py:54-73`：找空房从 `mon-a` 起并登记 `occupied`，但输出 `time_slot` 用的是 `TIME_SLOTS[idx % 5]`（`classroom.py:71`）。
- 实测：6 门课**全部从 mon-a 判定占位**，对外却声称 `mon-a/tue-b/wed-c/thu-d/fri-a` → 占位记录与展示结果对不上。
- 无教师冲突检查。
- `classroom.py:72` `note` 只区分"机房/普通"：物理实验→实验室1 却标注"普通教室"（实测可见）。
- `classroom.py:50` 本地又复制了一份 `TIME_SLOTS`，与 `constraints.py:43` 重复（重复定义坏味道）。

### 10. 工单 ID 跨重启重复 + 静默覆盖
- `ticket.py:49` `TK-{YYYYMMDD}-{_seq:04d}`，`_seq` 只在内存（`ticket.py:44`）→ 同一天服务重启后从 0001 重来。
- `db.py:104` `INSERT OR REPLACE` → **新工单会静默覆盖同 ID 的旧工单**（实测两次独立进程 ID 相同）。
- 修法：改用数据库自增主键 / UUID / 含毫秒时间戳。

### 11. 无鉴权、无 CSRF、debug 模式、XSS
- `webapp/` 全目录 0 处 `session/login/token/csrf`（grep 确认）→ 工单结案、能耗分析、排课求解接口**任何人可调用**。方向四是"管理与安全"，这是评审会重点挑的点。
- `run_web.py:25` 与 `app.py:178` `debug=True` → 开启 Werkzeug 交互式调试器（暴露面）+ 自动重载会重置全局状态。
- `ai.html:90,100` 用 `innerHTML` 拼接用户输入 `msg` 和 `answer` → 自 XSS；将来接入真实大模型输出直接进 `innerHTML`，**是存储 XSS**。

### 12. 数据无 run/batch 标识，反复运行互相污染
- `db.py:141` `save_schedule` 只追加不清旧 → `list_schedules(limit=100)`；实测反复运行 `6 → 12 → 18` 行，排课页把**多次遗传算法解叠在一起**，无法区分哪次是最新。
- `energy_forecast` 每次 24 行，`list_forecast(48)` 实测 48 行=**跨两次运行混合**。
- `energy_alerts` 无上限增长。
- 修法：加 `run_id`，查询只取最新一次 run。
